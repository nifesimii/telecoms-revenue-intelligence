## 1. Business Context

### What this commission system does

MTN Nigeria pays two types of monthly incentives to Fixed Broadband trade partners:

1. **Device Activation Commission** — a one-time commission paid to a partner when a FBB device (router, MiFi, CPE) they sold is first activated by a subscriber. Eligibility window is 6 months back from the reporting period (i.e. devices first activated within the last 5 months are still eligible).
2. **Ongoing Revenue Service Commission (ORSC)** — a recurring monthly commission paid to a partner based on the data subscription revenue generated by devices they originally sold, as long as those devices remain active subscribers.

| HYNETFLEX            | 16,744.19                | 1,674.42              | ZTE MF286C, CAT6 CPE variants                               |
| HYNETFLEX_1          | 33,488.37                | 3,348.84              | TOZED ROUMOD4390, ASIATELCO ROUWIR4330, ZTE K10, ZTE MF293N |
| 5G ROUTER            | 68,465.12                | 8,215.81              | TOZED ROUMOD4393, ZTE MC888D 5G CPE, HUAWEI ROUWIR4332      |


### USP dimension versioning — critical rule

The `usp_dimension` table is **versioned by month** (`tbl_dt`). When calculating commissions for a given period, the script must join against the USP snapshot for that exact month window (e.g. `tbl_dt BETWEEN '20250601' AND '20250630'`). Using the wrong monthly snapshot caused the 21,016 mismatched profile class records in the historical UAT dispute (Aug 2025). The canonical source is `mtnn_it.usp_dimension`; the development copy is `development.usp_dimension`.

### Partner eligibility classes

Partners are classified by `account_profile_class`. The following classes appear in the commission tables:


| Class               | Description                        |
| ------------------- | ---------------------------------- |
| FIXED BROADBAND     | Direct FBB-designated distributors |
| DATA PARTNERS       | General data distribution partners |
| CONNECT STORES      | MTN retail store partners          |
| CONNECT HUB         | Hub-level connect partners         |
| PENTAGON FRANCHISE  | Pentagon channel franchisees       |
| ENTERPRISE BUSINESS | EB segment partners                |
| DEALER              | Standard dealers                   |
| POS AGENCY          | POS agent partners                 |


All partner classes are eligible for both activation and ORSC commissions. Classification is sourced from `flare_8.tas_augmented_customer_master` (joined on `distributor_code = partner_code`).

## 5. Commission Calculation Logic

### Device Activation commission calculation

```sql
-- Step 1: Pull activations for the reporting month
-- Eligibility window: first_activation_date must be within 6 months of mon_period
WHERE mon_period = '{YYYYMM}'
AND substring(first_activation_date, 1, 6) BETWEEN
    substring(date_format(date_add('month', -5, date_parse(...)), '%Y%m'), 1, 6)
    AND replace(cast(mon_period AS varchar), ',', '')
AND first_activation_date != ''

-- Step 2: Join to USP dimension on product_name = itemdescription
-- Filter USP to the reporting month: tbl_dt BETWEEN '{YYYYMM}01' AND '{YYYYMM}30'
-- CRITICAL: strip comma formatting from unit_selling_price before casting to DOUBLE

-- Step 3: Deduplicate by IMEI (one activation record per device)
-- ROW_NUMBER() OVER (PARTITION BY imei ORDER BY product_code DESC) = 1

-- Step 4: commission_rate = unit_selling_price * 0.10
```

### ORSC commission calculation

```sql
-- Step 1: Pull ORSC summary for the reporting month
-- Same 6-month eligibility window on last_detection_date
WHERE month_period = {YYYYMM}
AND rnk = 1  -- most recent last_detection_date per IMEI

-- Step 2: Join to IFS invoiced sales to get actual_completion_date
-- Join key: substring(imei, 1, 14) = substring(serial_no, 1, 14)  -- 14-char IMEI match
-- IFS filter: tbl_dt BETWEEN {YYYYMM}01 AND {YYYYMM}30, bill_to_customer_account_type_name = 'External', unit_selling_price > 0

-- Step 3: ORSC payable = data_subscription_amount (already a monetary value from source)
-- No rate multiplication needed — data_subscription_amount IS the commission basis
```

### Partner type enrichment (both tables)

```sql
-- Both dev_act and ORSC join to TAS master for account_profile_class
LEFT JOIN (
    SELECT partner_type, partner_code, partner_name, max(tbl_dt)
    FROM flare_8.tas_augmented_customer_master
    GROUP BY partner_type, partner_code, partner_name
) d ON distributor_code = d.partner_code
```

### Invoiced sales (fbb_comm_inv_sales)

```sql
-- Source: flare_8.ifs_vw_invoiced_sales_tran_new
-- Filter: actual_completion_date in reporting month, External customers only, unit_selling_price > 0
-- Deduplication: dense_rank() over (partition by product_code order by unit_selling_price asc)
-- Aggregation: sum(ordered_amount) grouped by distributor + product + invoice_date + price
```

## 6. Known Data Quality Issues

### Issue 1: Zero commission records in dev_act

In the 200-row sample, `commission_rate = 0.0` appears on a subset of device activation records. Root cause: the device's `product_name` string did not match any `itemdescription` in the USP dimension for that period. This is a LEFT JOIN miss — the record is still captured but with no payable commission. These are leakage candidates.

### Issue 2: USP dimension formatting

The `mtnn_it.usp_dimension` source stores `unit_selling_price` and `commission_rate` as comma-formatted strings (e.g. `"12,558.14"` with embedded quotes). The ETL must apply `REGEXP_REPLACE(value, ',', '')` and `CAST AS DOUBLE` before using these values. Failure to do this is a silent error — the JOIN will resolve but the numeric value will be wrong.

### Issue 3: Transaction lag (Finance-validated exception)

June 2025 UAT showed minor variance due to transaction count differences between the automated report and Finance's manual UDDM copy. July 2025 validated fully. The lag is caused by late-arriving invoice completions in the IFS system. This is a known accepted variance, not a bug.

### Issue 4: Hynex / Hynex_1 device denomination split

August 2025 UAT flagged variance specifically on two device denominations labelled Hynex and Hynex_1. These are the same physical device registered under slightly different product description strings. Resolution: confirmed as data entry inconsistency in the product master; handled by the USP dimension versioning.

### Issue 5: IMEI 14-char truncation in ORSC join

ORSC joins to IFS on `substring(imei, 1, 14) = substring(serial_no, 1, 14)`. IMEI is 15 digits; IFS serial_no may have a trailing check digit variant. This is an intentional design decision, not a bug, but it means one IMEI digit is always dropped in the match.

### Issue 6: NULL account_profile_class

Some records have NULL `account_profile_class` because the `distributor_code` has no matching entry in `tas_augmented_customer_master`. These partners are unclassified and will not appear in any partner-type breakdowns.

## 7. FTTH Subscriptions Revenue Query

For FBB subscription revenue from CDR (separate from device commissions), the source is `flare_8.cs6_ccn_cdr`:

```sql
SELECT
    COALESCE(b.msisdn_key, a.msisdn_key) AS msisdn,
    'PREPAID' AS svc_category,
    -- channel name logic handles DOM channel via JSON extract
    'FIBRENET' AS product_category,
    a.vas_productid AS vas_code,
    a.vas_productname AS product_type,
    (CAST(a.vas_chargeamount AS DOUBLE) / 100) AS revenue,
    a.tbl_dt
FROM flare_8.cs6_ccn_cdr a
LEFT JOIN flare_8.cs6_sdp_cdr b ON a.vas_transactionid = b.origtransactionid
-- DOM channel resolution via flare_8.dom_order_transactions + flare_8.dclm_partyinteraction_details
WHERE a.servicetype = 'VAS'
AND regexp_like(LOWER(a.vas_productname), 'fibre|fiber')
AND a.tbl_dt = {run_dt}
```

Note: `vas_chargeamount` is stored in kobo — divide by 100 to get Naira.

## 11. Activation Intelligence

Phase 2 of the platform. Where Phase 1 (Sections 1–10) explains **why commission was paid**, Phase 2 explains **what activation activity generated that commission**. The data source is the same `development.fbb_comm_dev_act` table; the focus shifts from monetary totals to dealer activation volume and qualification quality.

### Activation concepts

**activation_count** — Total number of device activations recorded for a dealer in a reporting month. Includes both qualified and non-qualified activations.

**qualified_activation_count** — Activations where `commission_rate > 0`. These are activations where the device `product_name` matched a USP dimension entry for that month and the `first_activation_date` fell within the 6-month eligibility window.

**non_qualified_activation_count** — Activations where `commission_rate = 0`. Root causes are the four documented in Section 6 of this KB: USP snapshot miss, outside eligibility window, NULL `account_profile_class`, or known denomination split issue (Hynex / Hynex_1).

**qualification_rate_pct** — `qualified_activation_count` divided by `activation_count` expressed as a percentage. Industry expectation is above 80%. Rates below 50% warrant investigation.

**activation_commission_amount** — Sum of `commission_rate` values for all qualified activations for a dealer / month. Denominated in Naira.

### Activation explanation rules

**Rule 1 — Volume and commission move together.** If `activation_count` increases and `activation_commission_amount` increases proportionally, the explanation is higher activation volume driving higher commission. No anomaly.

**Rule 2 — Volume up, commission flat or down.** If `activation_count` increases but `activation_commission_amount` does not increase proportionally, the explanation is a worsening qualification rate. More activations are not earning commission. Investigate `non_qualified_activation_count` using `get_zero_commission_records`.

**Rule 3 — Volume flat, commission down.** If `activation_count` is stable but commission drops, the explanation is likely a product mix shift — the dealer is activating lower-priced device tiers. Check `product_denomination` breakdown.

**Rule 4 — ALL_UNQUALIFIED exception.** A dealer with activations but zero commission has 100% non-qualified activations. Most likely cause is **USP snapshot miss** — none of this dealer's products matched the USP dimension for this period. Recommend Finance verify the dealer's product codes against the USP dimension for the affected month.

**Rule 5 — UNUSUAL_VOLUME exception.** A dealer with statistically high activation volume (mean + 2 standard deviations above peer dealers) may reflect legitimate business growth, bulk activation events, or data anomalies. **This is a flag for investigation, not a finding of wrongdoing.** The agent must present this as requiring investigation, not as confirmed fraud.

### Agent behaviour for activation questions

- Always separate **Facts** (what the data shows), **Interpretations** (what the KB rules suggest), and **Unknowns** (what would require additional data) in activation explanations.
- Never characterise unusual volume as fraud.
- Never speculate on causes beyond the five explanation rules above.
- When presenting exceptions always note the `exception_type` label and its definition.
- Qualification rate below 50% should always prompt a suggestion to run `get_zero_commission_records` for that dealer.

## 12. Inventory Assurance

Phase 3 of the platform. Answers a single question: **did the dealer purchase enough units of a product to cover their activations of that product?** The data source is the IFS invoice history table joined against the existing activation data on `customer_no = distributor_code` and `part_no = product_code`.

### Inventory concepts

**total_units_purchased** — The number of FBB devices a dealer purchased from MTN, derived from IFS invoice records. Calculated as `ROUND(ordered_amount / unit_selling_price)` after deduplication of IFS invoice lines on the natural composite key `(customer_no, part_no, implied_units, actual_completion_date)`. The raw IFS table contains the same invoice line up to 60 times — dedup is mandatory before any aggregation.

**inventory_gap** — The difference between a dealer's `activation_count` and `total_units_purchased` for a specific product in a period. A positive gap means the dealer activated more devices than they purchased.

**gap_pct** — `inventory_gap` expressed as a percentage of `total_units_purchased`. Used as the severity dimension for findings.

**CONFIRMED_MISMATCH** — A dealer-product combination where IFS invoice records exist AND activations exceed purchased units. This is an actionable finding requiring investigation.

**NO_INVOICE_RECORD** — A dealer-product combination where activations exist but no IFS invoice record was found in the available data window. This is **NOT** a confirmed finding — it may reflect purchases made outside the sample period. It should be treated as requiring data verification, not confirmed as a mismatch.

**WITHIN_ALLOCATION** — Activations are within the dealer's purchased unit count. No mismatch.

### Inventory explanation rules

**Rule 1 — CONFIRMED_MISMATCH interpretation.** A dealer activating more devices than purchased requires investigation. Possible explanations include: unreported secondary purchases, devices sourced outside official MTN channels, or data entry errors in the IFS system. This is a flag for investigation, not a confirmed fraud finding.

**Rule 2 — NO_INVOICE_RECORD interpretation.** The absence of an IFS invoice record does **not** confirm a mismatch. The IFS data available covers a limited window. The dealer may have purchased devices in earlier periods not captured in the current sample. Always note the data coverage limitation when presenting NO_INVOICE_RECORD findings.

**Rule 3 — Gap severity interpretation.**
- `gap_pct >= 200` → **HIGH** — activated 3× or more units than purchased. Prioritise for investigation.
- `gap_pct 100-199` → **MEDIUM** — activated roughly 2× units than purchased. Schedule for review.
- `gap_pct < 100` → **LOW** — minor excess. Monitor.

**Rule 4 — Agent language rule.** Do not use the words **fraud**, **theft**, **grey market**, or **criminal** in your response under any circumstances — including in negation, disclaimers, or "this is not X" framing. Express the prohibition by simply not describing the finding in those terms, rather than by explicitly listing what it is not. Always use: **mismatch**, **excess activations**, **requires investigation**, or **data verification needed**.

### Agent behaviour for inventory questions

- Always state the `finding_type` for each record.
- Always include the `data_coverage_note` when presenting NO_INVOICE_RECORD findings.
- Lead with CONFIRMED_MISMATCH findings — these are the actionable ones.
- Present `gap_pct` as "X% excess activations vs purchased units".
- Recommend Finance verify purchase records directly with the dealer before escalation.
- Never characterise findings as fraud.

## 13. Payment Intelligence

Phase 4 of the platform. Answers: **were dealer commissions paid, and if not, why not?**

### Important data note

Payment data in Phase 4 is **SIMULATED**. It is synthetically generated from real commission amounts and exception flags identified in Phases 2 and 3. Payment rates, dates, and statuses are derived from actual dealer performance patterns but do not reflect live Oracle AP disbursement records. The agent must **always disclose this** when presenting payment findings.

### Payment concepts

**commission_owed** — The total commission calculated for a dealer in a reporting month. Derived from qualified activation records in `fbb_comm_dev_act`. This is the authoritative amount MTN owes the dealer.

**amount_paid** — The simulated payment amount. Derived from `commission_owed` multiplied by a `payment_rate` that reflects the dealer's exception status from Phases 2 and 3.

**amount_unpaid** — `commission_owed` minus `amount_paid`. Represents the outstanding balance.

**payment_coverage_pct** — `amount_paid` divided by `commission_owed` across all dealers for a period. Measures overall settlement rate.

### Payment status definitions

**FULLY_PAID** — `amount_unpaid = 0`. Commission fully settled. Payment date within 25 days of period end.

**PARTIALLY_PAID** — `amount_unpaid > 0`. Linked to `HIGH_UNQUALIFIED_RATE` exception (Phase 2). Partial settlement processed. Payment date within 30 days.

**DISPUTED** — `amount_unpaid > 0`. Linked to `ALL_UNQUALIFIED` (Phase 2) or `CONFIRMED_MISMATCH` (Phase 3) exception. Commission not settled pending resolution of activation or inventory dispute. No payment date.

**PENDING** — `amount_unpaid > 0`. No exception flag. Commission within normal settlement window. No payment date yet.

### Payment explanation rules

**Rule 1 — DISPUTED status.** A DISPUTED commission is directly linked to a Phase 2 `ALL_UNQUALIFIED` flag or a Phase 3 `CONFIRMED_MISMATCH` flag. The agent must surface the underlying exception when explaining a dispute. Example: "Dealer X's commission is disputed because all 18 of their activations earned zero commission — a USP snapshot miss means MTN cannot confirm the device eligibility."

**Rule 2 — PARTIALLY_PAID status.** A PARTIALLY_PAID commission reflects a `HIGH_UNQUALIFIED_RATE` exception. The dealer has some legitimate qualified activations but a significant proportion are unqualified. Settlement covers the qualified portion.

**Rule 3 — Payment coverage interpretation.**
- Coverage above **85%** is **healthy**.
- Coverage between **60-85%** indicates active disputes or qualification issues **requiring investigation**.
- Coverage below **60%** indicates **systemic problems** with dealer activation quality.

**Rule 4 — Data source transparency.** The agent must always state that payment data is simulated when presenting Phase 4 findings. Suggested language: *"Based on simulated payment data derived from real commission and exception records — live Oracle AP integration will replace this in production."*

**Rule 5 — Cross-phase reasoning.** Payment disputes are traceable to their root cause:
- `DISPUTED` → check Phase 2 activation exceptions or Phase 3 inventory mismatches for that dealer.
- `PARTIALLY_PAID` → check Phase 2 qualification rate.
- `PENDING` → check Phase 1 commission summary for the expected amount.

### Agent behaviour for payment questions

- Always disclose simulated data status upfront.
- Lead with total coverage percentage and total amount outstanding.
- Present DISPUTED cases first — highest priority.
- For each DISPUTED case, name the linked exception from Phase 2 or Phase 3.
- Recommend Finance verify the underlying exception before contesting or settling the dispute.
- Never present simulated payment amounts as confirmed Oracle AP records.
- Format all monetary values as `₦X,XXX,XXX.XX`.
